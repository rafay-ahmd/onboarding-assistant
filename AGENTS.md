# Agent guide: Onboarding Assistant

## Purpose and product direction

Hackathon 26: Automate Onboarding for NewHires (submitted by Diana Tang; two-person team).
Start with Dealertrack developers, then support other teams and locations through profiles.
Reduce time to a usable development environment by requesting access early, identifying blockers, and automating approved setup and verification steps.
The intended product goes beyond a tracker. The current implementation is the initial local prototype; do not describe planned integrations as working features.

Read README.md, package.json, and relevant implementation files before changing behavior. This guide describes the baseline as reviewed on October 15, 2026; inspect current code for subsequent changes. Keep this file and README.md updated when functionality or ownership changes.

## Current functionality: implemented

- A buildless browser dashboard served by a small Node.js HTTP server on loopback, port 4173 by default.
- A single draft Dealertrack developer profile: access requirements, routing, required fields, setup steps and dependencies.
- A shared new-hire details form. It fills request drafts; it is not an EM login or workflow trigger.
- Access requests tab: separate copyable drafts, a dedicated admin-rights form link, manual ticket links and manual statuses.
- Access states: not-requested, requested, granted, verified, blocked. Granted is distinct from verified.
- Workstation checks tab: import a JSON report generated by the local PowerShell script, or load clearly labelled fictional reports.
- The checker inspects local tools, Visual Studio, framework reference assemblies, expected Oracle/repository paths, LFS asset sizes, shared DLL presence and IIS mappings where permitted.
- The checker writes a report; it does not install software, change configuration, read credentials, authenticate, access remote services, restore packages or build applications.
- Setup journey tab: manually recorded completion and dependency blockers. It does not inspect individual installations or run setup.bat.
- Browser-local persistence for one hire's details, access statuses and setup completion. Clear the plan before switching hires. Imported reports remain in memory.
- Dependency reconciliation invalidates downstream completion when prerequisites are no longer verified.

## Not implemented yet

- Authentication, multiple users, role-based authorization or location-based assignment.
- Shared database or a multi-user backend. server.mjs currently serves a fixed list of static files and supports GET only.
- Live Slack submission, real helpdesk ticket creation, automatic status retrieval, reminders or escalation. A mock queue is now implemented (see update below).
- Running workstation checks from the dashboard (currently run the script separately and import its JSON).
- Automatic installations, builds, remote machine management or setup execution/resume.
- An MCP server or direct Codex integration.

## Agreed work split

Explore and implement:
- Multiple logins / roles: individual new hire, engineering manager (EM), and network team assigned by location.
- Profile-based dashboards appropriate to each role.
- An MCP server through which Codex can interact with explicitly exposed application capabilities.

These are planned capabilities, not existing behavior. Exact permissions, identity provider, persistence, location routing and MCP transport/tools remain design decisions to agree on.
Real role separation needs backend-enforced authorization and durable per-user data; hiding controls in the UI or using a localStorage role switch is only a demo.

### Rafay's stream: Slack and helpdesk integration

Investigate and implement supported ways to:
- Prepare and submit individual access requests through Slack/helpdesk.
- Associate each request with its actual helpdesk ticket.
- Retrieve ticket status and reflect progress in the app.
- Reduce back-and-forth by collecting required manager/group/account information upfront.

Before changing shared server routes, request/state contracts or persistence, coordinate the contract between streams. Do not overwrite unrelated work; inspect working-tree changes first. This ownership note is context, not authorization to message another chat or send external communications.

## Confirmed onboarding facts and open integration questions

- The user had to request Jira, Confluence and other entitlements separately; the helpdesk bot then granted them. Generate one request per access.
- Admin rights took the longest and use a dedicated form:
  https://go.helpdesk.autoscout24.com/servicedesk/customer/portal/105/create/471
- An AWS request needs an explicit group or mirroring information. TR-RO-AWS-DEALERTRACK-DEV was the user's requested group, not a universal default.
- Ticket status is visible on the authenticated helpdesk site. Example URL shape:
  https://go.helpdesk.autoscout24.com/servicedesk/customer/portal/105/OET-29575
- Slack bot/app acceptance, on-behalf-of submission, scopes, supported ticket APIs and authentication are not yet confirmed.
- A sent Slack message does not prove a ticket was created; ticket creation does not prove access works. Model these separately when integrating.
- The EM owns team requirements and entitlement confirmation. The Dealertrack profile still needs EM review.
- The user's account existed before day one. Do not assume that timing for every hire; check identity availability before early requests.
- Request independent permissions in parallel, start slow approvals early, and surface which request blocks setup. Do not bypass approvals or admin restrictions.

## Run and verify

No npm dependency installation is currently required.

    node server.mjs

Open http://127.0.0.1:4173. Node must be installed/on PATH; do not hardcode a developer's Codex-bundled runtime path into the app.

    node --test tests/*.test.mjs
    pwsh -NoProfile -File ./scripts/Test-OnboardingReadiness.ps1

The checker writes reports/readiness.json by default. Import it in Workstation checks. Use an approved PowerShell runtime and leave execution policies unchanged. A non-elevated process does not establish that the user lacks admin entitlement; denied inspection is blocked rather than missing.
For UI changes, verify affected flows in the browser. For integration logic, test success, denial, retries and duplicate prevention using mocks before live requests.

## Workstation and data constraints

- The user's PC is already configured. Do not uninstall dependencies, reset IIS, overwrite machine.config/tnsnames.ora or rerun setup.bat to test onboarding.
- Test installation/configuration actions in an approved disposable Windows VM with snapshots. Local inventory can be tested read-only on the working PC; its only intended write is the report/output directory.
- Keep requests drafted/mocked until the user explicitly authorizes live external submission. Authorization to develop integrations is not authorization to request actual access for people.
- Keep tokens/passwords out of source, drafts, reports, logs and localStorage. Future integrations need approved credential storage and authentication.
- Preserve ignores for actual reports and screenshots. Commit fictional fixtures, not machine reports or real hire records.
- Found on disk is not verified working. Do not infer access, successful builds or application readiness from an inventory result.

## Existing setup automation and reference material

Reuse and improve around the upstream setup.bat rather than recreating all provisioning logic.
It clones repos, configures Windows/IIS and copies configuration/assets, but it does not complete account access, authentication, all dependencies or application verification.
A rerun can replace machine.config and tnsnames.ora; existing app pools may be skipped rather than corrected. A wrapper alone does not make it safe or resumable. Future execution needs explicit stages, preflight checks, backups and post-step verification.

## Request queue increment (October 15, 2026)

Implemented on access-request-improvements: review/justification dialog, one browser-local mock request per employee/profile/entitlement, simulated delivery and failure/retry, uncertain-delivery reconciliation, follow-up questions/replies, fictional ticket creation, denial, grant and simulated verification. It does not send externally or update the existing real manual access/setup states.

New modules: web/request-queue.mjs (domain), web/mock-slack-adapter.mjs (no-network transport), web/request-queue-ui.mjs (UI/persistence), web/request-queue.css. Tests: tests/request-queue.test.mjs. Read docs/request-queue-contract.md before connecting authentication, persistence, backend routes or MCP tools.

The shared server remains static/GET-only; only asset routes were added. The existing state shape and storage key are unchanged. The mock queue uses its own versioned key and normalized email as a temporary identity; replace with an authorized immutable user ID and durable idempotency before live integration. Planned cross-stream API contracts remain to be agreed.

Access-card display synchronization: queue changes notify app.mjs, which projects matching employee/profile/entitlement progress into clearly labelled Mock badges. Actual manual state and setup dependency rules remain unchanged; header counts distinguish actual and mock verification. See accessCardStatus and its identity-isolation test before changing this mapping.

Queued access cards now use an automatic read-only status field; the unrelated manual real-access record is collapsed by default. Do not present a manual not-requested dropdown as the primary status of a completed mock request. Preserve manual data and real dependency isolation.

Card styling uses shared typography, spacing, field heights and palette in web/style.css, with only queue/dialog-specific layout in request-queue.css. Request text uses the same sans-serif font as the dashboard; code commands alone use monospace. The optional real helpdesk ticket link is a bookmark only, with no status synchronization.
